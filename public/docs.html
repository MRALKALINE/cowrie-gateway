KassifyPay API

Accept mobile money and card payments in Ghana. You create a charge from your server, send the customer to our checkout, and we tell you when the money has arrived.

Base URL https://cowrie-gateway.onrender.com — every path below is relative to it. All requests and responses are JSON.

How a payment works

1
Create a chargeYour server calls POST /api/charges with the amount. You get back a reference and a checkout_url.
2
Send the customer to the checkoutRedirect them to checkout_url. They choose mobile money or card and approve the payment on their phone.
3
We return them to youWhen they finish, we send them to the callbackUrl you supplied.
4
Confirm before you credit anythingA webhook arrives at your endpoint, and you can call GET /api/charges/:reference/verify. Never credit an account on the redirect alone.

API keys & modes

Your keys are in the dashboard under API keys. There are four, in two pairs:

KeyWhere it belongs
cowrie_sk_live_…Secret, live. Server-side only. This one takes real money.
cowrie_pk_live_…Publishable, live.
cowrie_sk_test_…Secret, test.
cowrie_pk_test_…Publishable, test.

Send the key on every API call, either way:

http
X-Public-Key: cowrie_sk_live_xxxxxxxxxxxxxxxx

# or
Authorization: Bearer cowrie_sk_live_xxxxxxxxxxxxxxxx

The key decides the mode. There is no separate mode parameter — a key containing _live_ creates live charges, anything else creates test charges.

Test mode cannot take payments Our payment provider has no sandbox, so a test charge can be created but never paid — the checkout will refuse it. Test keys are for wiring up the request and response shapes. To test the full flow end to end, use a live key and a small real amount, then refund it out of band.
Live keys need a verified account Until your business is verified in the dashboard, live keys return 403. Complete verification before you go live, not on launch day.

Quick start

Charge a customer GHS 50 and send them to the checkout.

cURL
curl -X POST https://cowrie-gateway.onrender.com/api/charges \
  -H "Authorization: Bearer cowrie_sk_live_xxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-10482" \
  -d '{
    "amount": 5000,
    "currency": "GHS",
    "email": "ama@example.com",
    "callbackUrl": "https://yoursite.com/payment/return",
    "metadata": { "orderId": "10482" }
  }'
Response 201
{
  "charge": {
    "reference":   "cwr_9f2a1c7b4e8d3a60",
    "amount":      5000,       // what you receive, in pesewas
    "feeAmount":   150,        // our fee, added on top
    "totalAmount": 5150,       // what the customer pays
    "currency":    "GHS",
    "status":      "pending",
    "mode":        "live"
  },
  "checkout_url": "https://cowrie-gateway.onrender.com/checkout?reference=cwr_9f2a1c7b4e8d3a60"
}
Node.js
const res = await fetch('https://cowrie-gateway.onrender.com/api/charges', {
  method: 'POST',
  headers: {
    'Authorization':   `Bearer ${process.env.KASSIFY_SECRET_KEY}`,
    'Content-Type':    'application/json',

header('Location: ' . $body['checkout_url']);

Amounts & fees

Amounts are in minor units Pesewas, not cedis. GHS 50.00 is 5000. Sending 50 charges fifty pesewas. Minimum 100 (GHS 1), maximum 100000000 (GHS 1,000,000).

Our fee is added on top of your amount rather than taken out of it. You are paid exactly what you asked for; the customer covers the fee.

FieldMeaningExample at 3%
amountWhat you receive5000 — GHS 50.00
feeAmountOur fee150 — GHS 1.50
totalAmountWhat the customer is charged5150 — GHS 51.50
feeBpsRate applied, in basis points300 — 3%

Your rate is set on your account. Each charge records the rate it was priced at, so a rate change never alters charges already created. Reconcile against amount — that is your money.

Create a charge

POST/api/charges
FieldTypeNotes
amountintegerRequired unless openAmount. Minor units.
currencystringDefaults to GHS.
emailstringCustomer email. Optional.
callbackUrlstringWhere we return the customer after the checkout.
metadataobjectAnything you want back later — order id, user id. Returned on the charge and in webhooks.
openAmountbooleantrue lets the customer type the amount at the checkout. Omit amount.
referencestringYour own reference. We generate one if you do not.
partnerstringPartner code, if this deposit was brought in by one. See Partner attribution.

Idempotency

Send an Idempotency-Key header — your order id works well. If the same key arrives twice we return the original charge with 200 instead of creating a second one. Without it, a retried request charges the customer twice.

Retrieve a charge

GET/api/charges/:reference

Public — no key required, since the checkout page itself uses it. Returns only what a payment page needs to display.

Response 200
{
  "charge": {
    "reference":       "cwr_9f2a1c7b4e8d3a60",
    "amount":          5000,
    "feeAmount":       150,
    "totalAmount":     5150,
    "currency":        "GHS",
    "status":          "pending",     // pending | success | failed
    "method":          "mobile_money",
    "openAmount":      false,
    "merchantName":    "Your Business",
    "merchantWebsite": "https://yoursite.com"
  }
}
Treat the reference as a secret Anyone holding it can read the charge. Do not put it in a public page, a URL you share, or an email subject line.

Verify a payment

GET/api/charges/:reference/verify

Re-checks the payment with the provider and returns the current charge. This is the authoritative answer — call it before you credit anything.

Never trust the redirect A customer landing on your callbackUrl proves nothing: they can reach that URL by typing it. Always confirm with verify or a webhook before releasing goods or crediting a wallet.
Node.js — on your return page
const ref = req.query.reference;
const r = await fetch(
  `https://cowrie-gateway.onrender.com/api/charges/${ref}/verify`
);
const { charge } = await r.json();

if (charge.status === 'success') {
  // Check the amount too — never take the status alone.
  const order = await orders.byChargeReference(ref);
  if (charge.amount >= order.totalMinor && !order.paid) {
    await orders.markPaid(order.id);
  }
}

Webhooks

Set your endpoint in the dashboard under Webhooks. We POST to it when a charge reaches a final state.

EventWhen
charge.successPayment confirmed. The money is yours.
charge.failedPayment failed or was never approved.
Request we send
POST https://yoursite.com/webhooks/kassifypay
Content-Type: application/json
cowrie-signature: 9c1f…   (HMAC-SHA256 hex of the exact body)

{
  "id":        "evt_a1b2c3d4e5f6",
  "type":      "charge.success",
  "createdAt": 1785859573641,
  "data":      { /* the full charge, including your metadata */ }
}

Verify the signature

Sign the raw request body with your webhook secret (dashboard → Webhooks) and compare. Anyone can POST to your endpoint; the signature is what makes it trustworthy.

Node.js / Express
const crypto = require('crypto');

// The raw body is required — JSON.stringify of a parsed object will not match.
app.post('/webhooks/kassifypay',
  express.raw({ type: 'application/json' }),
  (req, res) => {
    const expected = crypto
      .createHmac('sha256', process.env.KASSIFY_WEBHOOK_SECRET)
      .update(req.body)
      .digest('hex');

    const got = req.get('cowrie-signature') || '';
    const ok = expected.length === got.length &&
      crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(got));
    if (!ok) return res.status(400).end();

    const event = JSON.parse(req.body);
    if (event.type === 'charge.success') {
      creditOrder(event.data.metadata.orderId, event.data.amount);
    }
    res.sendStatus(200);          // reply fast; we time out at 10s
  });
PHP
$raw = file_get_contents('php://input');
$expected = hash_hmac('sha256', $raw, getenv('KASSIFY_WEBHOOK_SECRET'));
$got = $_SERVER['HTTP_COWRIE_SIGNATURE'] ?? '';

if (!hash_equals($expected, $got)) { http_response_code(400); exit; }

$event = json_decode($raw, true);
if ($event['type'] === 'charge.success') {
    credit_order($event['data']['metadata']['orderId'], $event['data']['amount']);
}
http_response_code(200);
Webhooks are not retried We send once and give up after 10 seconds. If your endpoint is down, that notification is gone. Delivery attempts are logged in the dashboard under Webhooks, but you should also reconcile: for any order still unpaid after a few minutes, call verify.
Make your handler idempotent Check whether the order is already paid before crediting. A webhook and your own verify call can both land for the same payment.

Requirements for your endpoint

  • Must be reachable on the public internet over http or https. Private and internal addresses are refused.
  • Must respond within 10 seconds. Acknowledge first, do the work afterwards.
  • Any 2xx counts as delivered.

Partner attribution

If people bring you deposits and earn a share, add their code to the charge you already create. Every deposit carrying it is credited to them, and their earnings are tracked for you.

JSON
{
  "amount":   5000,
  "currency": "GHS",
  "partner":  "kwame-mensah",
  "metadata": { "orderId": "10482", "userId": "u_8891" }
}

The code is read from partner, partnerCode, ref, affiliate or agent — at the top level, inside metadata, or as a query parameter. Use whichever your system already calls it.

An unknown code will not fail the payment Losing a real deposit to a typo would be worse than losing the attribution. The charge still goes through, and the unrecognised code is flagged in the console so nobody quietly goes unpaid.

Partners can also be given a ready-made link — /p/<code> — which raises a fresh deposit tagged to them on every visit. Ask your account manager to set one up.

Payment links

No code needed. In the dashboard, Payment links creates a URL you can send by WhatsApp or SMS. Set a fixed amount, or leave it open for the customer to type one.

One link, one payment A payment link is a single charge, spent the moment somebody pays it. For a link you can reuse, use a partner link instead.

Errors & limits

Errors are JSON with a message written for a person:

Response 400
{
  "error":   "client_error",
  "message": "amount must be an integer in minor units between 100 and 100000000"
}
StatusMeaning
400Something in your request is wrong. The message says what.
401Missing or invalid API key.
403Account locked, or a live key on an unverified account.
404No charge with that reference.
409The charge is no longer pending.
429Rate limited. Wait for Retry-After seconds.
500Our fault. The body carries a ref — send it to support and we can find the exact failure.

Rate limits

Per IP address, per minute: 200 requests overall, 60 charge creations, 20 payment actions. Back off on 429 rather than retrying immediately.

Go-live checklist

  • Business verified under Verification in the dashboard — live keys return 403 until it is.
  • Secret key in an environment variable, never in client-side code or version control.
  • Webhook URL set, signature verified, handler idempotent.
  • Idempotency-Key on every charge creation.
  • Amounts in pesewas — the commonest integration bug is out by a factor of 100.
  • Nothing credited on the redirect alone; always verify or wait for the webhook.
  • A reconciliation job that re-checks anything still pending after a few minutes.
Need a hand? Message us from the Support tab in your dashboard. Include the charge reference or the error ref and we can trace it exactly.
